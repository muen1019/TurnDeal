# 條件交換協商設計草案

狀態：2026-09-12 使用者已確認並要求實作。後續五種 Persona 指示已整合；目前實作與測試規格見 [SELLER_PERSONAS.md](SELLER_PERSONAS.md)。本文件保留原審閱草案，舊 D／E 展示描述由新版 Persona 取代。

## 目標與現況

讓 Buyer 能主動問「同價加送滑鼠墊」、「不要滑鼠墊可以再便宜多少」，並依 Seller 的回覆繼續還價。沿用五家、最多五輪；每家是否讓價、贈品可否折現與可讓多少，由賣家的私有設定決定。

目前 Buyer 只有 negotiate/stop 與競爭價格索引，Seller 只有主商品價格與 include_bundle；贈品與折扣由固定策略組裝。下一輪模型沒有完整的自家協商訊息，HTML 也沒有顯示對話。因此只修改 prompt 無法可靠支援條件交換。

本草案依工作目錄目前使用的 v0.3 契約提出擴充；本回合附帶的舊 AGENTS 指向 v0.1，兩者有差異。契約審閱時需明確沿用目前 v0.3，不能把既有 consumer 降回歷史版本。

## 對外可見的協商

以下為設計示例，非已執行的模型對話或報價：

| 輪次 | Buyer | Seller |
| --- | --- | --- |
| 1 | 請提供滑鼠報價。 | 單買 650 元，目前尚未附贈滑鼠墊。 |
| 2 | 650 元可以加送一張滑鼠墊嗎？ | 可以，單買或附滑鼠墊都是 650 元。 |
| 3 | 如果不要滑鼠墊，可以改成 600 元嗎？ | 600 元無法接受；不含墊最低可報 620 元，含墊則 650 元。 |
| 4 | 那不含墊可以 610 元嗎？ | 不含墊 620 元是本次最終報價。 |

這是可以出價、拒絕條件並回覆替代條件的協商；Seller 拒絕一次還價不等於拒絕整個分支。模型不保證一定走滿示例輪次或成功取得優惠。

## Buyer 的能力

- 可要求降價、同價加贈、取消贈品換折扣，或請賣家同時提供單買與組合價。
- 可提出自己的整數 TWD 還價，不再只能選其他賣家的既有價格；自主出價不得描述成已存在的競爭報價。
- 根據使用者偏好、自家已驗證報價及自家已提交的協商紀錄，決定下一步。每輪同時提出明確的商品組合與目標總價，避免只議價而不清楚議哪個方案。
- 明確不要配件時只議單買；未授權加價時不能自行提高配件額度。停止協商不表示替使用者採用或購買。
- Buyer 看不到 Seller 底價、贈品成本或可折現上限。

## Seller 的能力與設定

新增私有設定 `gift_exchange_discount_twd`（預設 0）：放棄滑鼠墊時最多額外讓多少 TWD。這是折讓上限，不是模型必須報出的折扣，也不是滑鼠墊零售價。

取消贈品折讓必須綁定自家先前已驗證、仍有效且相同 SKU 的含墊報價。Backend 計算可報區間，套用商品底價；不能每輪重複累加同一筆贈品折讓。沒有贈品、贈品缺貨、SKU 不同或政策不允許時，不得憑空折現。

單買與組合分別報價並各自檢查履約、底價與同款前次報價。Seller 可以接受條件、回覆替代条件、拒絕該項條件並維持報價，或結束整個分支；拒絕原因不可洩漏私有底價與政策。

建議展示配置：A 維持讓價、B 維持快速配送、C 在免費贈品策略上增加「最多折現 30 元」、D 保留組合比單買便宜 30 元且不折現、E 維持固定價。以上 C 的新設定待確認，既有 fixture 先保留。

## 免費與加價必須忠實判定

若同輪單買 620 元、組合 650 元，配件差額就是 30 元，即使前輪稱作贈品，這輪也不能標示免費。

- `related_no_extra_cost`：620 元單買可合格；650 元組合為 needs_confirmation，不進 Evaluator。
- `related_with_cap` 且額度至少 30 元：兩者都可合格，但仍須符合總預算與其他硬條件。
- `disabled`：不能提供已授權的搭售方案。

沿用目前同輪 standalone baseline 與 bundle eligibility 的語意，不透過虛增單買價格製造假免費。基準更新時產生新的 Offer ID，歷史報價與已發布快照不改寫。

## 契約與實作變更提案

先審閱新增的 optional 契約與示例，再改 consumer；Evaluator Structured Outputs 不變。

1. SellerRFQ 增加 optional `proposal`：意圖（降價／加贈／取消贈品換折扣／比較）、目標組合、目標總價、自家參考 Offer ID。舊 RFQ 沒有 proposal 時保持原行為。自家參考 ID 必須屬於該分支且仍有效，不能傳入其他賣家 ID。
2. SellerNegotiationResult 增加 optional 條件回覆：accepted／countered／declined，對應正式 drafts。Backend 依實際商品與價差驗證，不能只信 accepted 文字。現有 offered/refused 與 is_final 繼續控制分支生命週期。
3. Buyer/Seller 的內部模型輸出新增上述決策與訊息；Seller 對 standalone/bundle 分開定價。舊呼叫端由 adapter 保持可用，不直接變更既有共用 Offer 形狀。
4. SellerSalesProfile 與 SQLite migration 新增可折現上限；預設 0，舊設定與歷史資料保持原本商務行為。
5. Manager 將已提交且只屬於該分支的協商紀錄帶到下一輪。保存 proposal、模型回覆、Backend 驗證結果與 provider；逾時的遲到訊息不可進下一輪。
6. HTML 每輪顯示 Buyer 要求、Seller 回應、正式單買／組合價、條件是否達成、是否 fallback。可見文案由已驗證結構化決策產生；若保留模型原話，明確區分原話與有效報價，不能將原話當作商務承諾。不得將私有 audit 原封不動輸出。

## 驗證計畫

測試透過 BuyerAgent.negotiate、SellerAgent.negotiate 與整場 negotiate 的入口觀察結果，並驗證 Backend 的正式 Offer 與公開報告。

- 加贈成功、沒有可用滑鼠墊、政策拒絕、使用者禁用配件。
- 取消贈品成功換折扣、折扣不足時還價、觸底、不允許折現、重複要求不能疊加折扣。
- 單買與組合價差正確；預設不允許付費配件、明示額度不足與足夠的結果不同。
- 下一輪依自家前輪回覆協商；拒絕一項條件不會錯誤終止整個分支。
- 自主還價不可冒充競爭報價；引用其他分支 ID、失效 Offer 或更換 SKU 時拒絕錯誤參考。
- 無效模型決策／API 失敗使用符合相同政策的 deterministic fallback；正式报价、歷史與最終結果可重播。
- 五家離線整場測試保留五種策略，HTML 可讀到條件交換與最終方案；再以真實模型跑一次並記錄實際對話投影、排序、耗時、用量與 fallback。

真實模型測試驗證商務約束與可追蹤結果，不斷言模型每次說相同句子或給相同價格。本次未追加模型 API 呼叫。
