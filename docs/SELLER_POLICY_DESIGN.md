# Seller 策略、商品底線與協商狀態：最新設計

更新日期：2026-09-12。

狀態：本文件保留完整目標設計。使用者確認後，本次已實作 Persona 賣家投影、SKU 成本與議價範圍、售後偏好匹配；完成範圍與尚未支援的通用規則見 [SELLER_POLICY_IMPLEMENTATION.md](SELLER_POLICY_IMPLEMENTATION.md)。下文的「目前狀態」表保留設計提出時的基準，實作現況以該文件為準。

## 核心決策

保留 prompt 表達賣家的商業目標與協商偏好；DB 保存可機器驗證的底線、能力與狀態。Backend 每輪先計算合法方案及價格範圍，LLM 再從中選擇，Backend 最後獨立驗證完整草稿。

不把整套策略 prompt 複製到每個 SKU。賣家共用策略，個別商品設定自己的底線；需要特殊處理的 SKU 可有明確的策略覆寫。硬性規則即使也寫在 prompt 中，仍由 Backend 執行。

底價、成本、讓利上限與私有策略內容不參與 Orchestrator 排序。Orchestrator 使用公開商品條件選擇合格賣家；Persona 是預先登錄的賣家屬性，不直接成為排名加分項。Seller 只讀自己的私有政策，Buyer 與 Evaluator 只取得允許公開的正式條件。

## 一、資料分成三層

| 層級 | 保存內容 | 識別與範圍 |
| --- | --- | --- |
| 賣家策略與共用能力 | Persona、商業目標、籌碼偏好、預設停止規則、物流／售後能力、會員規則、共用券額度、prompt 版本 | seller_id |
| 商品私有政策 | 底價、成本、最低利潤率、可搭配品、贈品與降價上限、庫存壓力、必要的策略覆寫 | seller_id + sku_id；同賣家同 SKU 有多個刊登或活動時，再以 listing_id／policy_scope 區分 |
| 協商狀態 | 固定價格基準、歷史報價、已讓步次數、已用折現額度、已承諾權益、停止原因 | request_id + seller_id；不同 SKU 的報價基準分別記錄 |

上述是邏輯分層，不要求立即建立三張全新的表。現有 seller_inventory、seller_persona_policies、seller_benefit_catalog 與協商提交紀錄應優先沿用或擴充。權益定義及共用庫存只維護一份，SKU 政策以 ID 引用。

現有 canonical catalog 使用 product_id，Discovery 使用 listing_id；實作前須明確建立映射，不能把文件中的 sku_id 直接當成兩者可互換的新欄位。

有效政策由「賣家預設＋明確的商品覆寫＋適用條件」解析。商品覆寫可以替代標示為可覆寫的預設，但不能提高賣家共用硬上限、創造履約能力或放寬買家授權。必要欄位缺失或互相矛盾時，該商品不可進入新政策議價；不能把缺值解讀成無限制或零成本。

### Persona 預先存入賣家資訊

Persona 在賣家建檔／Demo seed 時指定並持久化，不是 Orchestrator 選出五家之後才按名次或隨機分派。每場協商讀取該賣家既有的 Persona 與有效政策版本，不能為了湊出五種展示結果而臨時改寫賣家策略。

賣家資訊在邏輯上包含以下欄位；這是目標資料形狀，不是本次新增的 API 契約：

| 資訊 | 內容與來源 |
| --- | --- |
| seller_id、name、enabled | 既有賣家基本資料 |
| persona | price_optimizer、speed_seller、bundle_curator、loyalty_builder、margin_guardian 其中一種；由賣家設定，不由模型猜測 |
| strategy_policy_ref | 指向自己的版本化私有策略，供 Backend 與自己的 Seller Agent 讀取，不輸出完整政策給 Discovery |
| public_service_options | 指向已登錄、可驗證且可公開的服務條件；區分原本即適用的條件，以及需協商或滿足資格才可提供的選項 |

現有展示設定已將 Persona 保存於 seller_persona_policies.policy_json 的 persona 欄位，並以 seller_id 關聯 sellers。後續可在賣家資料讀取層組合成 seller.persona，不必再建立另一個容易不同步的 Persona 欄位。現有 Orchestrator list_sellers 與 Discovery Seller DTO 尚未提供此欄位，本次文件更新不改動這些介面。

舊賣家若未配置 Persona，需明確標示未配置；不能依入選順序自動補上身分，也不能因此推定具備特定物流或售後能力。

### Orchestrator 如何匹配買家偏好

目標是按使用者偏好匹配賣家實際提供的商品與公開服務，不直接用 Persona 名稱給分。Persona 描述商業取向，不保證本次最便宜、最快或售後最好；私有底價、預計可砍價空間、贈品成本及尚未同意的權益不作為已成立的條件。

| 使用者偏好 | 目標匹配依據 | 目前狀態 |
| --- | --- | --- |
| 價格低 | 公開含稅運總價；明確區分「越便宜越好」與「接近某個目標價」 | Discovery 已有 price_first 權重，但價格分數是接近 target_total_twd；沒有 target 時價格權重為零，尚不等於一般最低價排序 |
| 交期快 | 配送目的地適用且可驗證的公開交期 | 已有 delivery_first 及 delivery_days_max；目前以 Catalog delivery_days 評分，更細地區／截單能力屬後續設計 |
| 售後好 | 適用商品的公開保固範圍、退貨期、客服與換貨條件及履約證據 | 尚未提供專屬售後偏好與評分；trust_first 目前提高賣家市場評分權重，不能當成售後能力分數 |
| 希望有組合或會員福利 | 實際適用的公開組合／權益及資格條件 | 本設計的後續擴充；不能把未來券當成立即降價，或把可談贈品當成已贈送 |

售後偏好的解析、可公開服務欄位、硬性要求與軟偏好的分別、缺資料處理及評分口徑，須先明確定義再更新 Formatter／Discovery 契約與測試。缺少售後資料應標示未知，不能由 Persona 補造；買家明訂必要保固條件而無證據者，不可當作合格候選。

Orchestrator 比較協商前已知條件並選出候選；協商後仍由 Evaluator 排序 Backend 驗證的實際 Offer。將售後正式納入最後推薦也是另一個明確的評分變更，不能只更新探索排序就宣稱最終推薦已支援。

### Demo 固定配置

Demo 預先建立 A 清庫、B 物流、C 組合、D 回購、E 售後五家賣家，並配置相符的商品、私有政策及模擬履約能力。以固定 Catalog 快照與展示需求，讓五家符合硬條件並經正常 Orchestrator 流程入選。

一般資料集的自然排序前五家可能出現相同 Persona，這是允許的。Demo 透過測資保證策略多樣性，不加「每種 Persona 必須各選一家」的排序或補位規則，不讓不合格賣家為了展示而進入協商。改變需求導致不足五家時如實回報，不臨時更換 Persona。

## 二、22 項政策因素

以下名稱是目標設計用語，尚非新增的正式 schema。金額使用整數 TWD；正式報價始終包含稅與運費。

| # | 因素 | 主要保存位置 | 定義與 Backend 責任 |
| --- | --- | --- | --- |
| 1 | price_floor_twd | 商品 | 最低含稅運成交總價，明確區分單買與組合的適用規則。可映射現有 floor_price_twd；不可誤用舊政策不含運的 floor_item_price_twd。 |
| 2 | cost_components | 商品＋共用能力引用 | 商品、贈品、物流、平台費、服務等成本及計算口徑；區分總成本與相對基準新增成本，避免重複計入。 |
| 3 | min_margin_bps | 商品，可繼承預設 | 最低政策利潤率，1500 表示 15%；明定收入扣稅與成本口徑，不直接宣稱等同會計毛利率。 |
| 4 | total_concession_budget_twd | 商品，可繼承預設 | 每筆完整成交方案的整體讓利上限，合併價格折讓及新增權益的預算占用。 |
| 5 | bundle_eligible_skus | 商品 | 搭配白名單、數量與免費／付費模式。仍須驗證相關性、庫存、條款及買家授權；本版最多一張滑鼠墊。 |
| 6 | gift_cost_budget_twd | 商品 | 每筆方案贈品成本總上限，以成本而非標價計算。 |
| 7 | gift_exchange_discount_cap_twd | 商品 | 取消贈品可換取的額外現金折讓上限，按整場協商累計，不等於贈品成本。 |
| 8 | benefit_combination_rules | 賣家預設＋商品例外 | 權益的疊加、互斥與交換規則；移除贈品折現後不能同時保留同一贈品。 |
| 9 | voucher_options | 賣家權益目錄，商品引用 | 合法券 ID、面額、門檻、有效期、適用範圍、使用次數及疊用條件。 |
| 10 | voucher_budget | 賣家共用額度＋商品上限 | 每筆方案的券面額總上限與共用發放額度；面額和內部成本預算分別記錄。 |
| 11 | loyalty_rules | 賣家，商品可限制適用性 | 新客／舊客／會員權益、資格證據與上限；不推定會員資格或自動加入會員。 |
| 12 | shipping_capability | 賣家能力目錄，商品引用 | 按地區、截單時間、方式列出可承諾交期、成本與證據；組合須同時符合配件履約條件。 |
| 13 | warranty_options | 賣家能力目錄，商品引用 | 保固方案、總期限或延長期限、保障範圍、除外條件、成本與履約證據。 |
| 14 | service_options | 賣家能力目錄，商品引用 | 退貨、瑕疵換貨、客服、晚到補償等正式方案，附條件、成本、額度與證據。 |
| 15 | negotiation_strategy | 賣家，商品可明確覆寫 | 商業目標、籌碼偏好與開放條件。偏好進入 prompt；禁止降價、指定 SKU 等硬規則結構化驗證。 |
| 16 | inventory_pressure | 商品 | 庫存壓力及更新時間，供策略參考；不取代實際庫存，不放寬硬性上限。 |
| 17 | max_concession_count | 賣家預設＋商品限制 | 最多讓步次數，依已提交的條件改善計算；一輪同時改善多項算一次，重播不重算。 |
| 18 | max_discount_per_step_twd | 商品，可繼承預設 | 相對上一筆可比較報價的單次降價上限；相同 SKU、數量及方案口徑才可直接比較。 |
| 19 | max_total_discount_twd | 商品，可繼承預設 | 相對固定開價基準的整場降價上限，不得每輪重新設定基準。 |
| 20 | policy_scope | 賣家／商品政策 | 適用 SKU、顏色、數量、地區、刊登及活動期間；不能把清庫優惠套用到其他庫存。 |
| 21 | policy_version | 所有政策及能力定義 | 報價記錄實際使用版本；歷史報價不可被新政策改寫。 |
| 22 | quote_ttl_seconds | 賣家預設＋商品限制 | 從 Backend 發行時計算有效期，不能超出所需政策、權益及履約條件的有效期。 |

原有售價、規格、實際庫存、基本條款及來源資料繼續存在，不由這 22 項政策取代。

## 三、prompt 與 Backend 的責任

### Prompt 表達策略，模型做範圍內的選擇

Seller 輸入包含自己的商業目標、有效私有政策摘要、Backend 算出的合法選項、Buyer 的正式提案，以及已提交的自家協商狀態。模板及策略設定都有版本，避免另有一份手寫 prompt 與 DB 規則互相矛盾。

模型可決定本輪是否讓步、合法範圍內的價格、提供哪個已登錄權益、拒絕單項要求或提出最終報價。它不能修改政策、補造成本、庫存、券、服務或履約證據。

| Persona | Prompt 引導的商業偏好 | Backend 強制的邊界與停止條件 |
| --- | --- | --- |
| 清庫型 Price Optimizer | 優先加快指定商品周轉，逐步讓價 | 指定庫存、底價、利潤率及單次／累計上限；額度耗盡或達停止條件即 final |
| 履約型 Speed Seller | 保護物流溢價，優先改善運送條件 | 價格保護政策、配送能力及補償額度；無可新增物流籌碼時可 final |
| 組合型 Bundle Curator | 優先提供相關配件，再考慮條件交換 | 搭配白名單、贈品成本、折現額度及互斥規則；可交換空間耗盡時可 final |
| 關係型 Loyalty Builder | 優先提供回購及彈性權益 | 券額度、資格、使用條件；不扣本次價格；無可新增權益時可 final |
| 服務型 Margin Guardian | 保護品牌與利潤，優先改善售後 | 價格保護、服務目錄、成本及證據；無可新增服務時可 final |

停止協商不等於撤銷先前有效報價。既有報價繼續按原期限及條件處理。談判最多五輪，讓步次數是另一個計數，不可混用。

### Backend 驗證完整方案

Backend 驗證商品／數量、價格、利潤率、各項及合計預算、互斥條件、庫存、履約、權益資格、配件授權、政策版本及有效期。Seller 宣稱 accepted 或 final 不會略過檢查，eligible 與 immutable offer_id 仍由 Backend 產生。

合法選項可能具有不同價格下限：免費贈品組合、無贈品單買、加速配送方案應各自計算，不能給模型一個通用價格區間後任意拼接權益。

非法輸出不發布，也不偷偷改價後冒稱模型同意。依現有受限失敗處理使用合法 deterministic fallback；沒有合法方案時明確拒絕。fallback 通過相同驗證，不能繞過新底線。

## 四、價格與讓利計算口徑

固定價格基準在首次詢價前由 Backend 依適用 Catalog／政策快照取得，包含稅與運費，不讓 LLM 自訂較高開價來擴大折扣。不同 SKU 或方案的基準分開記錄，換品不能重置整場贈品折現或共用額度。

三類限制分別驗證：

1. 正式總價不得低於適用底價。
2. 以明定口徑計算的 `(淨收入 − 方案成本) / 淨收入` 不得低於 min_margin_bps／10000；收入須為正，必要成本不能缺失。實作使用整數比例比較及明確稅額取整規則。
3. 整體讓利占用＝相對固定基準的價格折讓＋新增贈品成本＋新增物流／服務成本＋未來權益的政策預算占用，不得超出 total_concession_budget_twd。

基本商品與原本配送成本用於利潤率計算；只有相對基準增加的部分列入新增讓利成本。取消贈品折現已反映在價格折讓中，不再加算一次。利潤率與讓利檢查是兩項獨立檢查，不把兩者結果相加。

券面額另受 voucher_budget 約束。尚無可靠成本模型的模擬券，建議保守以全額面額占用內部讓利預算；未來若採估計成本，必須有明確的版本化計算政策，不能讓模型猜兌換率。無論內部怎麼計算，未來券都不減本次成交價或 Evaluator 的價格比較值。

## 五、每輪流程與狀態

1. 從 SQLite 讀取有效政策、Catalog、履約證據及已提交協商狀態；每場綁定政策版本，動態庫存與能力仍重新檢查。
2. Buyer 提出有結構的降價、加贈、取消贈品換折扣、組合比較或權益請求。
3. Backend 依要求及剩餘額度，計算本輪合法方案、每個方案的價格區間與可選權益。
4. Seller LLM 依策略選擇方案或拒絕，回傳草稿。
5. Backend 獨立驗證、配置 offer_id，原子提交報價與狀態；同一輪重播不增加讓步次數或重複扣額度。
6. 繼續下一輪或依 final／拒絕／timeout／error／五輪上限停止；Evaluator 只排序完整、有效、eligible 的正式 Offer。

需保存的狀態包含：各 SKU 固定價格基準、上一筆有效報價、已讓步次數、累計降價、已使用贈品折現額度、每個方案的預算明細、已承諾及交換的權益、停止原因、政策版本。

方案可比性由 SKU、數量、變體及已登錄條件交換判定。同一輪的多個互斥選項不是多筆成交支出；重複相同報價不算新讓步；換方案不能藉此規避累計限制。新增權益算條件改善，已登錄的交換則記錄交換前後內容，不能任意撤掉已承諾權益。

賣家共用券額度與庫存另有可用、預留、消耗狀態，不隸屬某個模型。報價檢查可用量不代表已購買或已扣庫存；接受時原子預留、取消或到期釋放、兌換時扣除，並以 idempotency 防止重複處理。此完整預留流程屬後續交易整合，現有協商可用量檢查不能宣稱已完成預留。

接受與兌換仍須重新驗證必要條件及資源。新商業政策不回寫舊報價；原報價的版本／承諾適用性與目前履約能力分別檢查，失效時明確回覆原因。

## 六、條件交換範例

以下是設計示例，不是新的實測結果。某款滑鼠固定基準價 699、底價 599，贈品滑鼠墊成本 35、贈品預算 40，取消贈品最多額外折 20，整體讓利預算 100。假設必要成本、利潤率及其他條件均通過驗證。

Seller 策略：「優先用相關配件提高整組價值；買家不需要配件時，可考慮換成價格優惠。」目前報價是 649 元含滑鼠墊，尚未使用折現額度。

Buyer：「不要滑鼠墊，能不能 610 元？」

Backend 算出這次移除贈品最多額外折 20 元；在沒有其他合法價格讓步的前提下，該交換方案最低 629 元。Seller 可以還價 629 元、少折一些或拒絕這項交換，不能自行承諾 610 元。

| 方案 | 讓利占用 | 判斷 |
| --- | --- | --- |
| 649 元加滑鼠墊 | 50 元價格折讓＋35 元贈品成本＝85 元 | 通過這項預算限制 |
| 629 元、不含滑鼠墊 | 70 元價格折讓＝70 元 | 交換額度占用 20 元；不再加算已移除贈品成本 |
| 599 元加滑鼠墊 | 100 元價格折讓＋35 元贈品成本＝135 元 | 超出整體預算，即使沒有突破底價也不合法 |

若同時還有一般降價空間，Backend 應分別列出一般折讓與贈品交換額度，再驗證完整方案。贈品折現不是唯一降價來源，也不能隱藏在一般折讓中重複使用。
